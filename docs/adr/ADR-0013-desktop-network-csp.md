### ADR-0013 데스크톱 앱의 서버 요청은 웹뷰 fetch로 보내고, CSP에는 빌드할 때 정한 서버 주소 하나만 연다
- 상태: 채택
- 날짜: 2026-10-29
- 배경: ADR-0012로 데스크톱 앱은 Tauri v2이고 웹 클라이언트 코드를 함께 쓴다. 지금 데스크톱 CSP는 앱 자신과 Rust(IPC) 외의 네트워크를 모두 막는다. API 클라이언트를 만들려면 데스크톱 앱이 서버에 닿는 경로를 정해야 하는데, 이 경로는 복호화된 볼트가 밖으로 나갈 수 있는 출구이므로 보안 경계에 해당한다.
- 결정: (1) 데스크톱 앱도 브라우저와 같은 `fetch` 기반 API 클라이언트를 쓴다. (2) 서버 주소는 빌드할 때 `VITE_API_BASE_URL`로 정하고, 릴리스 빌드에서는 그 주소의 출처 하나만 CSP `connect-src`에 더한다(`tauri build --config`로 덮어씀). 와일드카드나 `https:` 전체는 허용하지 않는다. (3) 서버는 설정한 출처(데스크톱 앱 출처, Windows는 `http://tauri.localhost`)만 CORS로 허용하며 기본값은 비어 있다. (4) 개발 중에는 Vite 프록시(`/api` → 8080)로 같은 출처에서 요청하므로 CSP를 바꾸지 않는다.
- 고려했던 대안: (1) tauri-plugin-http로 Rust가 대신 요청 — CSP를 닫아 둘 수 있지만 외부 의존성이 늘고 웹과 데스크톱의 요청 코드가 갈라진다. 플러그인의 허용 주소 범위도 결국 같은 출구라 보안상 얻는 것이 적어 기각. (2) 직접 만든 Rust 명령(reqwest) — 경계는 가장 좁지만 API가 바뀔 때마다 Rust도 고쳐야 해 Phase 1 데모 규모에 과하므로 기각. (3) 사용자가 서버 주소를 입력(자체 호스팅) — 주소가 바뀌면 CSP를 고정할 수 없어 Rust 경유가 사실상 필요해진다. Phase 1 범위 밖이라 보류.
- 결과: 요청 코드가 하나라 테스트와 유지가 쉽고 새 의존성이 없다. 반면 악성 코드가 들어오면 열어 둔 서버 하나로는 요청을 보낼 수 있다(서버가 영지식 구조라 기존 위험 범위를 크게 넓히지는 않는다). 서버 주소를 바꾸려면 다시 빌드해야 하고, 서버에 CORS 설정이 생긴다. 자체 호스팅을 지원할 때 이 ADR을 대체한다.
- 관련: ADR-0004, ADR-0008, ADR-0012, SEC-002
