### ADR-0023 마스터 비밀번호 변경은 클라이언트가 볼트를 다시 암호화하고, 서버가 요청 하나로 인증 정보와 볼트를 함께 교체한다
- 상태: 채택
- 날짜: 2026-11-02
- 영역: 공통(백엔드, 모든 클라이언트)

> **요약** 클라이언트는 새 salt로 새 키를 만들고 볼트를 다시 암호화해, 현재 인증 해시와 함께 `POST /api/v1/auth/change-password` 한 번으로 보낸다. 서버는 KDF 값·인증 해시·볼트를 한 번에 교체하고 계정의 세션을 모두 끝낸 뒤 새 토큰을 준다. Secret Key는 이번에 도입하지 않는다.

#### 배경

마스터 비밀번호를 바꾸면 마스터 키, 인증 해시, 볼트 암호문이 모두 바뀐다(ADR-0008). 서버에서 셋 중 일부만 바뀌면 계정이 볼트를 열 수 없게 된다. 미결 질문은 키 교체 흐름을 만들 때 Secret Key(기기에서 만드는 추가 난수로 키를 만드는 방식) 도입도 함께 정하도록 했다.

#### 결정

1. **클라이언트 재암호화:** 클라이언트가 새 salt(16바이트)와 현재 반복 횟수로 새 키를 만들고, 화면의 볼트를 새 키로 다시 암호화한다. 서버는 평문을 보지 않는다.
2. **요청 하나:** 현재 인증 해시, 새 인증 해시, 새 KDF 값, 새 볼트와 기대 revision을 한 요청으로 보낸다(api-spec 2.5.5). 여러 요청으로 나누지 않는다.
3. **서버의 일괄 교체:** 서버는 현재 인증 해시를 확인하고 revision을 비교한 뒤 셋을 함께 교체한다. 한쪽만 바뀐 상태가 밖에서 보이지 않아야 한다. 저장소에서 이를 지키는 방법은 백엔드 ADR에 둔다.
4. **revision 연속:** 교체한 볼트의 revision은 이전 값에서 이어 올린다. 다른 기기의 되돌림 감지(VLT-001)가 깨지지 않게 하기 위해서다.
5. **세션:** 교체 뒤 계정의 세션을 모두 끝내고 바꾼 기기에만 새 토큰을 준다.
6. **시도 제한:** 현재 인증 해시 확인에 로그인과 같은 계정·IP 시도 제한을 적용한다. 훔친 세션 토큰으로 비밀번호를 대입하는 것을 막는다.
7. **Secret Key는 보류:** 서버 유출 시 오프라인 대입을 막는 효과는 크지만, 새 기기 로그인마다 Secret Key 입력이 필요하고 모든 플랫폼의 키 유도가 바뀐다. 데모 범위를 넘어 이번에는 도입하지 않는다.

#### 고려했던 대안

| 대안 | 고르지 않은 이유 |
| :--- | :--- |
| 인증 정보 변경과 볼트 저장을 두 요청으로 | 두 요청 사이에 실패하면 인증 정보와 볼트가 어긋나 계정이 열리지 않는다. |
| 키 래핑(볼트 키를 따로 두고 마스터 키로 감싸기) | 비밀번호를 바꿀 때 작은 키만 다시 감싸면 되지만, 볼트 형식과 모든 플랫폼의 키 구조가 바뀐다(ADR-0008·0011 대체). |
| 다른 기기 세션 유지 | 구현은 단순하지만 유출된 토큰으로 계속 암호문을 받을 수 있다. 다른 기기는 어차피 새 비밀번호 없이는 볼트를 열 수 없다. |
| Secret Key 함께 도입 | 결정 7 참고 |

#### 결과

- 장점: 실패해도 계정이 열리지 않는 상태가 생기지 않는다. 기존 KDF 변경 감지(SEC-003 규칙 11)를 그대로 써서 다른 기기가 안내를 받는다.
- 비용: 볼트 전체를 다시 암호화해 보내므로 볼트가 크면 요청이 크다(최대 5MB). 다른 기기의 올리지 못한 변경은 사라진다. 옛 백업은 옛 비밀번호로 연다.
