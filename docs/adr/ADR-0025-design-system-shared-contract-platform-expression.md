### ADR-0025 디자인 시스템을 공통 계약층과 플랫폼 표현층으로 나눈다
- 상태: 채택
- 날짜: 2026-11-11
- 영역: 공통

> **요약** 시맨틱 토큰 이름과 컴포넌트 계약(역할·변형·상태·접근성·문구)은 모든 클라이언트가 공통으로 쓰고, 재질·모양·모션·네이티브 컨트롤 같은 표현은 각 플랫폼의 디자인 언어(Apple Liquid Glass, Android Material 3)를 따른다.

#### 배경

[디자인 시스템](../design-system.md)은 모든 클라이언트가 "같은 이름과 값의 토큰, 같은 컴포넌트 규격"을 쓴다고 정해 두었다. 이 원칙을 그대로 지키면 두 가지 문제가 생긴다.

- Apple의 Liquid Glass나 Android의 Material 3처럼 OS가 주는 재질과 컨트롤을 쓸 수 없다. 앱이 그 OS답지 않게 보이고, OS가 업데이트되어도 앱 모습이 따라가지 않는다.
- 이미 코드가 문서와 어긋나 있다. 간격·모서리 토큰이 없어서 Apple Feature 화면에 `padding(12)`, `cornerRadius(8)` 같은 숫자가 직접 들어가 있다. 웹에는 문서에 없는 `Alert`, `ConfirmPrompt`, `ModalDialog`가 생겼다.

플랫폼을 늘려 가면서도 같은 제품으로 알아볼 수 있으려면, 무엇을 통일하고 무엇을 플랫폼에 맡길지 경계를 정해야 한다.

#### 결정

1. 디자인 시스템을 네 층으로 나눈다.
   - **브랜드·의미층(공통)**: 시맨틱 토큰 이름과 그 의미를 정한다. 예를 들어 `accent`는 안전, `destructive`는 위험을 뜻한다.
   - **컴포넌트 계약층(공통)**: 컴포넌트 이름, 역할, 변형, 상태, 접근성 요구, 사용자 문구를 정한다.
   - **표현층(플랫폼별)**: 재질, 모양, 모서리, 그림자, 모션, 타이포를 정한다.
   - **네이티브 컨트롤층(플랫폼별)**: 시스템 컴포넌트를 쓸지, 직접 만들지를 정한다.
2. 시맨틱 토큰은 이름을 공통으로 쓰되, 값은 플랫폼마다 달라도 된다. 단, 보안 상태 색(안전·위험)의 의미와 색상 계열은 모든 플랫폼에서 지킨다.
3. Apple은 시스템 재질과 컨트롤을 우선 쓴다. Liquid Glass를 직접 흉내 내지 않고, 브랜드 악센트만 입힌다.
4. Android(도입 시)는 Material 3의 `ColorScheme`에 시맨틱 토큰을 매핑한다. 보안 상태 색의 의미를 지키기 위해 다이내믹 컬러는 쓰지 않고 브랜드 색을 고정한다.
5. 데스크톱(Tauri)은 웹뷰를 쓰므로 웹의 표현을 그대로 따른다. 시스템 글꼴, 창 테두리, 메뉴처럼 OS가 직접 주는 요소만 OS를 따른다.
6. 공통 계약층의 원본은 레포 안에 둔다. 시각 카탈로그(Claude Design 등)는 이 원본을 보여주는 사본이다.
7. 공통 계약을 지키게 하는 장치는 정적 게이트로 만든다. 게이트는 플랫폼마다 토큰 이름이 빠짐없이 있는지, 계약에 있는 컴포넌트가 구현됐는지, Feature 코드에 숫자나 색상 리터럴이 직접 들어가지 않았는지를 검사한다. 구체적인 형식은 후속 결정으로 정한다.

#### 고려한 대안

| 대안 | 기각 이유 |
| :--- | :--- |
| 모든 플랫폼에서 토큰 값과 모습을 완전히 같게 유지(현행) | OS 디자인 언어와 부딪힌다. Liquid Glass나 Material 3 같은 시스템 재질을 쓸 수 없고, OS가 업데이트될 때마다 직접 따라가야 한다. |
| 공통 계약 없이 각 플랫폼이 자유롭게 설계 | 플랫폼마다 보안 상태의 표현과 문구가 달라진다. 사용자가 같은 제품으로 알아보기 어렵고, 공통 컴포넌트를 관리하는 구조 자체가 사라진다. |
| Figma 등 디자인 툴을 공통 원본으로 사용 | 디자이너가 없는 구조에서는 코드와 디자인 툴 두 곳을 손으로 맞춰야 한다. 문서와 코드가 어긋나는 지금 문제가 오히려 커진다. |
| 크로스 플랫폼 UI 프레임워크(Flutter, React Native 등)로 코드 자체를 공유 | [ADR-0010](ADR-0010-client-composition-ios-and-shared-web.md)의 iOS 네이티브 결정과 충돌한다. 이 방식으로는 네이티브 디자인 언어를 따르기도 더 어렵다. |

#### 결과

- 얻는 것:
  - 각 OS다운 모습을 유지하면서도 같은 제품으로 알아볼 수 있다.
  - 공통으로 관리할 범위가 계약과 의미로 좁아져서 게이트로 검증할 수 있다.
  - OS가 업데이트되면 시스템 컨트롤이 자동으로 따라간다.
- 비용:
  - [디자인 시스템](../design-system.md)의 원칙과 토큰 표를 "공통 이름 + 플랫폼 매핑" 구조로 다시 써야 한다.
  - 플랫폼마다 매핑 문서를 관리해야 한다.
  - 플랫폼마다 보이는 모습이 달라서 시각 카탈로그도 플랫폼별로 나란히 보여줘야 한다.
