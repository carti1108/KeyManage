### ADR-0016 Apple 클라이언트 협업 방식 비교 실험 (일괄 위임 + 역할 분리)
- 상태: 채택
- 날짜: 2026-10-30
- 배경: KeyManage는 영지식(Zero-Knowledge) 비밀번호 관리자이며, 웹 클라이언트(Windows 환경, Claude Code 에이전트)에서 암호 모듈과 볼트 동기화를 이미 구현하였다. 당시 웹 클라이언트는 단계마다 사람에게 질문·확인하고, 2종의 범용 리뷰(코드, 보안)와 CI 검증을 거치는 협업 방식을 취했다. 동일한 영지식 암호 및 동기화 기능을 Apple(iOS·macOS) 클라이언트에서 구현함에 있어, AI 에이전트와 사람 간의 협업 방식을 체계적으로 달리 적용하고 그 효과와 안전성을 정량적·정성적으로 측정하여 웹 방식과 비교·평가하기 위한 실험 설계가 필요하다.
- 결정: Apple 클라이언트 구현 시 다음 3가지 변수(주 변수 1개, 부 변수 2개)를 적용한 실험적 협업 모델을 채택한다:
  1. **주 변수: 사람 개입 방식 (일괄 위임, Batch Delegation)**
     - 기능 구현 착수 전, 사람이 판단해야 할 설계·정책 항목을 '결정표(Decision Table)' 하나로 종합하여 일괄 질의·확정한다.
     - 작업 진행 중에는 원칙적으로 사람에게 중간 질의를 하지 않고 사전 정의된 '가정(Assumption)'에 따라 자율적으로 진행한다.
     - 모든 가정은 `가정 N: 내용 / 근거 / 뒤집을 때 영향` 형식으로 로그와 PR에 명시적으로 기록한다.
     - 단, (a) 정책(`docs/policies/`) 변경, (b) 새 외부 의존성 추가, (c) 암호·키 유도·저장 데이터 형식·보안 경계 변경의 3대 안전 경계 위반 시에는 작업을 즉시 중단하고 사람에게 예외 질의한다(예외 중단 횟수 카운트).
  2. **부 변수 1: 리뷰 구조 (다층 분할 리뷰 및 강제 게이트)**
     - 범용 리뷰 대신 4개 레이어(Build & Infra, Core, Feature, Governance) 분할 독립 서브에이전트 리뷰와 전용 보안 리뷰(키·평문 유출, KDF 다운그레이드, IV 재사용, 에러 메시지 비밀 노출)를 실행하고, 워크플로우 강제 게이트(`apple-workflow-gate.md`)를 통해 P1/P2 결함 0건을 검증한다.
  3. **부 변수 2: 테스트·구현 작성자 분리 (역할 분리, Role Separation)**
     - `git worktree`로 작업 공간을 분리하고 상호 독립된 서브에이전트가 역할을 분담한다.
     - 테스트 작성 에이전트: 스펙(`docs/vault-spec.md`, `docs/api-spec.md`)과 테스트 벡터(`docs/crypto-test-vectors.json`)만 참조하여 Swift Testing 기반의 실패 테스트(RED)를 작성·커밋한다 (구현 코드는 일체 열람하지 않음).
     - 구현 에이전트: 테스트와 스펙만 참조하여 테스트를 통과(GREEN)시키는 코드를 구현·커밋한다. 테스트 코드는 임의 수정할 수 없으며, 테스트 오류 판단 시 근거와 함께 보고한다.
  4. **비교 변수 요약표**:
     | 변수 | 웹 (기준) | Apple (이번 실험) |
     |---|---|---|
     | **사람 개입 방식 (주 변수)** | 단계마다 질문·확인 | **A. 일괄 위임**: 시작할 때 결정표로 한 번에 묻고, 진행 중에는 가정으로 진행 |
     | **리뷰 구조 (부 변수)** | 범용 리뷰 2개 | 4레이어 분할 리뷰 + 보안 리뷰 + 강제 게이트 |
     | **테스트·구현 작성자 (부 변수)** | 같은 에이전트 | **B. 역할 분리**: 테스트 작성 에이전트와 구현 에이전트 분리 |
  5. **불변 통제 규칙 (스펙 우선 순수 구현)**:
     - 웹 구현 코드(`Apps/Web/`)는 일체 열람·검색하지 않으며, 스펙 문서와 테스트 벡터만으로 구현한다. 스펙 모호성으로 인한 판단은 '스펙 질문'으로 별도 기록한다.
- 고려했던 대안:
  1. 웹과 동일한 단계별 인터랙티브 방식 채택 — 안정적이나 에이전트의 자율성과 일괄 위임에 따른 생산성/오류율 변화를 실증할 수 없어 기각.
  2. 완전 자율(사람 개입 배제) 방식 채택 — 영지식 보안 경계 및 저장 데이터 형식 무결성을 위협할 위험이 너무 커 기각.
  3. '계약 우선(Contract-First)'을 주 변수로 두는 방식 — 웹 클라이언트 구현을 통해 이미 스펙과 테스트 벡터가 확정된 상태이므로, 이는 작업 순서 효과(Order Effect)에 불과하며 협업 방식의 독립 변수가 될 수 없어 기각.
- 결과:
  1. **측정 및 평가 지표**:
     - 결정표 항목 수, 진행 중 채택된 가정 수, PR 리뷰에서 기각/뒤집힌 가정 수.
     - 안전 경계 도달로 인한 예외 중단 횟수 및 사람 총 개입 횟수(결정표, 예외, 정정, 승인).
     - 레이어별 리뷰 지적 수(P1/P2/P3) 및 보안 리뷰 지적 수(확신도 8 이상/미만).
     - 구현 에이전트의 '테스트 오류' 보고 건수 및 실제 결함 판정 건수.
     - 스펙 모호성 질문 수, 테스트 첫 실행 실패 수, 규칙 위반 횟수, 총 소요 시간 및 토큰 비용.
  2. **비교의 한계와 통제**:
     - 주 실행 에이전트(Claude Code vs Gemini Antigravity)의 역량 차이 및 플랫폼 언어/프레임워크(TypeScript/React vs Swift 6/Tuist)의 생태계 특성이 정량적 지표에 혼입될 수 있는 본질적 한계가 존재함.
     - 스펙 문서 열람 통제 및 공통 테스트 벡터(100% 비트 일치)를 기준으로 기능적 등가성을 엄격히 통제하여 협업 프로세스 차이에 따른 순효과를 분리 관측함.
  3. **스펙의 객관성 및 SSOT(Single Source of Truth) 실증 (핵심 가치)**:
     - 웹 구현 코드(`Apps/Web/`)를 일체 열람하지 않고 오직 스펙 문서(`vault-spec.md`, `api-spec.md`)와 공통 테스트 벡터(`crypto-test-vectors.json`)만으로 구현을 완성함으로써, 완전히 다른 AI(Gemini)와 다른 언어(Swift) 환경에서도 비트 단위 동일한 영지식 암호 결과가 재현되는지 검증한다.
     - 재현 성공 시, 본 프로젝트의 스펙과 거버넌스가 특정 사람이나 특정 AI(Claude)에 종속되지 않은 **'플랫폼·에이전트 독립적인 진정한 SSOT(Single Source of Truth)'**임을 객관적으로 입증하는 결정적 성과를 확보한다.
- 관련: SEC-001, SEC-002, VLT-001, ADR-0001, ADR-0009, ADR-0011, ADR-0014, ADR-0015, 이슈 #40
