# 2026-10-31 · 웹 오프라인 저장 1단계: 연결이 끊겨도 수정 내용 유지 (#61)

> 요약: 웹 클라이언트에서 저장이 서버에 닿지 못하면 수정 내용을 동기화 대기로 메모리에 두고, 재연결·30초마다·잠금 해제 직후에 다시 올리게 했다. 기기 저장(재시작 뒤 오프라인 열기)은 디스크에 둘 범위만 ADR-0018로 정하고 구현은 다음 단계로 미뤘다. 무엇부터 할지와 저장 범위(토큰 제외)는 사람이 정했다. 독립 코드 리뷰와 보안 리뷰를 두 번 돌려 대기 내용이 사라지거나 덮어써지는 경로를 고쳤다.

## 사용 도구

- 도구: Claude Code (Claude Opus 5.5), Vitest, GitHub Actions
- 플러그인/스킬: `superpowers:brainstorming`, `adr-manager:adr-manager`, `policy-manager:policy-manager`, `code-review`(독립 서브에이전트), `security-review`(독립 서브에이전트), `project-docs:ai-usage`

## 요청

- 인수인계 메모의 다음 작업 1번(오프라인 저장)을 진행했다.
- AI가 "열어 둔 볼트가 연결이 끊겨도 수정을 잃지 않음(A)"과 "인터넷 없이 새로 열어도 볼트가 열림(B)" 중 무엇이 핵심인지 물었다. 사람은 A부터 구현하고, B는 디스크에 둘 범위를 ADR 초안으로 먼저 보여 달라고 했다. 토큰은 빼는 쪽을 추천했다.

## AI 산출물

- ADR-0018: 웹 클라이언트가 기기에 저장할 값(이메일, KDF 값, 암호화된 볼트, 기준 revision, 마지막으로 본 revision, 대기 표시, 레코드 형식 버전)과 저장하지 않을 값(세션 토큰, 키, 인증 해시, 평문)을 정했다. 저장소는 IndexedDB로 하고, 오프라인 잠금 해제 뒤 다시 로그인하는 흐름도 담았다.
- VLT-001 갱신
  - 어떤 저장 실패를 대기로 둘지: 네트워크 오류, 시간 초과, 5xx, 429, 응답 형식 오류
  - 다시 보내는 시점: 재연결, 30초마다, 잠금 해제 직후
  - 잠금과 세션 만료가 끼었을 때 대기 내용을 어떻게 남길지
  - 대기 중 로그아웃 확인 문구와 탭 떠남 확인
  - 받을 수 없는 대기 내용을 버리는 규칙
- `vaultSession.ts`
  - 먼저 이 기기에 반영한 뒤 서버로 보낸다. 보내기는 한 번에 하나씩 순서대로 한다.
  - 잠겨도 대기 내용을 암호화한 채 남긴다.
  - 세션이 만료돼도 대기 내용을 남겨, 같은 계정으로 다시 로그인하면 병합해 올린다.
  - `retryPendingSync`, `hasPendingSync`, `onSyncChange`를 추가했다.
- `vaultSync.ts`: 서버에 보내기 전에 검사하고 암호화만 하는 `seal`, 일시적 실패를 판정하는 함수, `RevisionMismatchError`를 추가했다.
- `app/pendingSyncWiring.ts`: `online` 이벤트, 30초 주기 재전송, `beforeunload` 떠남 확인을 연결했다.
- 화면: 대기 중 오프라인 경고, 재전송 오류 표시, 볼트 화면과 잠금 화면의 로그아웃 확인을 만들었다.
- 테스트: 세션 대기 테스트 24건, 연결부 5건, 화면 9건을 새로 썼다. 함께 쓰는 가짜 서버는 `src/test/sessionFixtures.ts`로 분리했다.

## 사람의 판단

- A(메모리 안의 대기)를 먼저 하고, B(기기 저장)는 범위를 ADR로 먼저 확인받는 순서로 정했다.
- 기기에 세션 토큰을 저장하지 않는 쪽을 골랐다.
- A 설명과 ADR 초안은 AI가 보여 준 그대로 승인했다.

## 검증

- 로컬 `npm run check` 통과(단위 테스트 381건, 이전 343건). `Scripts/check-docs.sh` 통과.
- PR #62 CI: 첫 푸시에서 6개 작업 모두 통과. 그 뒤 수정 푸시의 결과는 PR에서 확인한다.
- 독립 코드 리뷰 1차
  - HIGH 4건: 저장이 거절된 뒤 화면이 옛 볼트를 보여 줘서 다음 수정이 대기 중인 변경을 덮어씀. 잠긴 상태에서 탭을 닫을 때 확인이 없음. 잠금 화면에서 로그아웃할 때 확인이 없음. 로그인에 실패만 해도 대기 내용이 지워짐.
  - MEDIUM 4건, LOW 3건.
  - LOW 1건(재전송 때 다시 암호화하는 비용)을 빼고 모두 반영했다.
- 독립 보안 리뷰: CRITICAL·HIGH·MEDIUM은 없고 LOW 4건이 나왔다. 계정 간 유출 경로는 없다고 확인했다. LOW-2(대기 내용이 있어도 잠금 해제 때 먼저 되돌림 검사)와 LOW-3(이전 세션의 늦은 오류)를 반영했다.
- 같은 코드 리뷰어의 재확인: 원래 지적은 모두 해결됐다고 확인했다. 대신 수정이 새로 만든 문제 4건이 나왔고, 모두 반영했다.
  - HIGH: 받을 수 없는 대기 내용이 같은 계정 로그인을 계속 막음.
  - MEDIUM: revision 불일치를 일시적 실패로 숨김.
  - LOW 2건.

## 검증하지 못한 것

1. 브라우저에서 개발자 도구로 오프라인을 켜고 끄는 동작은 직접 확인하지 않았다. 화면 테스트와 연결부 테스트로만 확인했다.
2. 2차 수정(받을 수 없는 대기 내용 처리, revision 불일치)은 테스트로만 확인했고, 리뷰어의 세 번째 확인은 받지 않았다.
3. 실제 서버 통합 테스트에는 오프라인 시나리오를 넣지 않았다. 네트워크를 끊어야 해서 단위 테스트로 대신했다.

## AI의 오류와 정정

1. 처음 구현에서 저장 함수가 이 기기에 먼저 반영한 뒤 오류를 던지는데, 화면이 그 경우 상태를 다시 읽지 않았다. 그래서 다음 수정이 대기 중인 변경을 지울 수 있었다. 리뷰에서 발견해 고쳤다.
2. 잠긴 상태와 세션 만료 뒤에 남은 대기 내용을 떠남 확인과 로그아웃 확인에서 빠뜨렸다.
3. 세션 만료로 남긴 대기 내용을 로그인을 시작할 때(인증 전에) 지웠다. 그래서 이메일 오타 한 번으로 데이터가 사라질 수 있었다.
4. 이 3번을 고치면서 대기 내용을 성공할 때만 지우게 바꿨는데, 그러자 서버가 받을 수 없는 대기 내용이 같은 계정 로그인을 계속 막는 새 결함이 생겼다. 재확인 리뷰에서 발견해 고쳤다.
5. 잠금 해제 때 대기 내용이 있으면 서버 볼트를 먼저 받지 않고 바로 저장했다. 그래서 서버가 기준과 같은 revision으로 되돌아간 경우를 잡지 못했다.
6. 테스트를 쓰다가 쓸모없는 줄을 남겼고, 경합 테스트 하나는 요청이 도착하기 전에 잠가 다른 이유로 실패할 수 있었다. 커밋 전에 고쳤다.
