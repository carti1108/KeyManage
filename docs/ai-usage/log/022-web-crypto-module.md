# 2026-10-29 · 웹 클라이언트 암호 모듈 구현 (#32)

> 요약: 웹 MVP 두 번째 단계로 키 유도와 볼트 암·복호화를 WebCrypto로 구현했다. 플랫폼 간 테스트 벡터와 결과가 같은지 확인했고, 독립 보안 리뷰에서는 확신도 8 이상의 취약점이 나오지 않았다. 코드 리뷰 지적 9건은 모두 반영했으며, 그중 반복 횟수 상한과 깨진 유니코드 비밀번호 거절은 정책 문서에도 추가했다.

## 사용 도구

- 플러그인/스킬: `superpowers:test-driven-development`, `code-review`(Claude Code 내장, 독립 서브에이전트), `security-review`(Claude Code 내장), `policy-manager:policy-manager`, `issue-worktree:commit-rules`, `project-docs:ai-usage`

## 요청

- 앞 단계 PR을 머지했다는 알림과 함께, 웹 코드 계획의 다음 단계(암호 모듈)를 이어서 진행하라는 요청.

## AI 산출물

- `keys.ts`: 비밀번호 전처리(NFC, 지정 공백 6종만 앞뒤 제거), PBKDF2 600,000회 → HKDF로 암호화 키(꺼낼 수 없는 AES-256-GCM 키)와 인증 해시 분리, 서버가 준 반복 횟수·salt 검증.
- `vaultCipher.ts`: AES-256-GCM 암·복호화, 헤더(version·cipher)를 AAD로 인증, 태그 분리 저장, 키 오류(`VaultDecryptError`)와 형식 오류(`UnsupportedPayloadError`) 구분.
- `base64.ts`: 표준 Base64만 허용하는 변환기.
- 테스트: `docs/crypto-test-vectors.json`의 모든 케이스로 전처리 결과·인증 해시·암호화 키·페이로드를 대조.
- 문서: vault-spec 2장에 깨진 서로게이트 거절, SEC-002에 반복 횟수 상한 10,000,000 추가.

## 사람의 판단

## 검증

- `npm run check`(타입 검사, 린트, 테스트 28건) 통과.
- 독립 보안 리뷰: 확신도 8 이상의 취약점 없음. 낮은 확신도로 남은 지적(깨진 서로게이트의 플랫폼 간 차이)은 거절 규칙으로 반영.
- 독립 코드 리뷰 9건 반영. 새 동작은 테스트를 먼저 써서 실패를 확인한 뒤 구현했다.

## 검증하지 못한 것

1. iOS(CryptoKit) 구현과의 실제 상호 운용은 iOS 단계에서 같은 테스트 벡터로 확인한다.
2. JavaScript 문자열로 받은 비밀번호 원본은 메모리에서 지울 수 없다. 화면 단계에서 오래 들고 있지 않도록 해야 한다.

## AI의 오류와 정정

1. 반복 횟수의 하한만 검사해, 서버가 지나치게 큰 값을 내려주면 기기가 오래 멈출 수 있었다. 리뷰 지적으로 상한을 두고 정책에 기록했다.
2. `sealVault`가 IV를 인자로 받을 수 있어 실수로 같은 IV를 다시 쓸 여지가 있었다. 고정 IV는 테스트 전용 함수로 분리했다.
3. Base64 오류와 문자열이 아닌 필드를 키 오류로 보고해, 형식 문제를 "비밀번호가 틀림"으로 오해하게 만들 수 있었다. 형식 오류로 구분했다.
4. `atob`의 너그러운 해석(공백, 패딩 누락 허용)을 그대로 따라 플랫폼마다 판단이 갈릴 수 있었다. 표준 형식만 허용하게 바꿨다.
5. 작업 중 파일 편집 스크립트가 쓰기 도중 실패해 `keys.ts`가 빈 파일이 되었다. 커밋된 내용으로 되돌린 뒤 다시 고쳤다.
