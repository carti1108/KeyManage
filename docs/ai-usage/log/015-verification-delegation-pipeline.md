# 2026-10-28 · 검증 위임 체계 구축: CI, 뮤테이션 테스트, 독립 리뷰 (ADR-0009)

> 요약: 사람의 검증 시간이 병목이라는 문제의식에서 출발해, 검증을 CI 기계 판정·PIT 뮤테이션 테스트·작성 맥락과 분리된 독립 리뷰로 위임하는 체계를 ADR-0009로 정하고 구축했다. 첫 CI가 통과했고, 뮤테이션 테스트와 독립 리뷰가 각각 AI 자기 검증으로는 놓친 문제를 찾아냈다.

## 사용 도구

- 도구: Claude Code (Claude Opus 5.5), GitHub Actions
- 플러그인/스킬: `adr-manager:adr-manager`, `code-review`(Claude Code 내장, 독립 서브에이전트), `issue-worktree:commit-rules`, `project-docs:ai-usage`

## 요청

- AI 시대에는 사람의 검증 시간을 줄이는 것이 가장 중요하다는 문제의식과 함께, AI 검증을 어떻게 믿을지, 위임 범위는 어디까지인지, 마지막에 사람이 무엇을 검증해야 하는지에 대한 의견과 참고 자료를 요청받았다.

## AI 산출물

- 검증 신뢰 4단계(기계 판정, 테스트 자체 검증, 독립 리뷰, 명세 대조)와 위험도·되돌리기 쉬움 기준의 위임 범위, 사람의 최종 확인 대상(의도, 증거 요약, 데모 한 번) 제안. 지금까지 CI 없이 로컬 결과를 말로 전했고 독립 리뷰를 한 번도 하지 않았다는 점을 함께 밝혔다.
- 참고 자료 조사(Addy Osmani "Trust, But Verify", Simon Willison의 vibe engineering, Anthropic 서브에이전트 가이드, 뮤테이션 테스트 연구 등)와 2차 자료 수치에 대한 주의.
- [`docs/adr/ADR-0009-verification-delegation-pipeline.md`](../../adr/ADR-0009-verification-delegation-pipeline.md), 이슈 #21.
- `.github/workflows/ci.yml`, `Scripts/mutation-score.py`, `.github/pull_request_template.md`, `:domain` PIT 설정, `gradlew`·`check-docs.sh` 실행 권한, 루트 CLAUDE.md 한 줄.
- 언어별 뮤테이션 테스트 도구 비교(Swift는 Muter가 있으나 덜 성숙함).

## 사람의 판단

- 검증 위임 체계와 ADR-0009, PIT 플러그인 도입, 루트 CLAUDE.md 수정을 승인했다.
- 독립 리뷰를 의무화하는 방향에 동의했다.

## 검증

- 첫 CI 실행(backend, docs 작업) 통과.
- 뮤테이션 테스트 첫 측정: 라인 커버리지 95%인데 점수 66%. Kotlin 컴파일러 null 검사 결함을 제외하고 빈틈을 보강해 88%, 리뷰 반영 후 86%.
- 뮤테이션 테스트가 찾은 실제 빈틈: `AuthHash`·`ServerSecret`의 `toString` 마스킹(로그 유출 방지) 미검증, `Revision(0)` 경계값 미검증. 테스트를 보강했다.
- 독립 리뷰(`/code-review`, 작성 맥락과 분리된 서브에이전트) 지적 10건 중 8건 반영, 1건 일부 반영, 1건은 원래 예정된 작업(이 로그).

## 검증하지 못한 것

1. 뮤테이션 하한선은 ADR-0009대로 아직 정하지 않았다. 여러 PR에서 기준선이 안정된 뒤 정한다.
2. 뮤테이션 테스트는 `:domain`에만 적용했다. `:infrastructure`·`:api`는 후속이다.
3. 로그인 시도 제한 상태가 실패한 이메일마다 메모리에 쌓이는 문제는 잠금 만료 시 정리하도록 일부 줄였을 뿐, 근본 대책(상한·주기적 정리)은 IP 제한과 함께 #19에서 설계한다.

## AI의 오류와 정정

1. ADR-0009에 "처음에는 기록만 하고 기준선이 잡히면 하한선을 정한다"고 써 놓고, 같은 PR에서 하한선 80%를 걸었다. 독립 리뷰가 ADR과 구현의 불일치로 지적해 하한선을 제거했다.
2. 뮤테이션 점수 스크립트가 `KILLED`만 검출로 세어 PIT 자체 판정과 달라질 수 있었고, `<init>` 같은 메서드 이름을 이스케이프하지 않아 표에서 사라졌다. 독립 리뷰 지적으로 고쳤다.
3. "다른 값이면 hashCode도 달라야 한다"는 단언은 equals·hashCode 계약이 요구하지 않는 구현 세부였다. 독립 리뷰 지적으로 삭제했다.
4. 뮤테이션 테스트 결과만 보고 잠금 만료 시 상태를 정리하던 줄을 "불필요한 코드"로 지웠는데, 독립 리뷰가 상태가 남는 문제와 메모리 누적을 지적했다. 만료 시 항목을 지우도록 다시 고쳤다. 뮤테이션 테스트의 "동작이 같다"는 신호가 곧 "필요 없다"는 뜻은 아니라는 교훈을 남긴다.
