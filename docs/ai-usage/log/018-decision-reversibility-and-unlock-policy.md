# 2026-10-28 · 결정 확인 기준 조정과 잠금 해제 정책(SEC-003)

> 요약: 1Password와 기능 구조를 비교한 뒤 잠금 해제 정책을 추가했다. 그 과정에서 사용자가 "구현체 교체가 쉬운 구조인데 왜 이렇게 신중한가"를 짚었고, 결정을 되돌리기 쉬운 것과 비싼 것으로 나눠 확인 절차를 차등 적용하도록 루트 CLAUDE.md 규칙을 바꿨다.

## 사용 도구

- 도구: Claude Code (Claude Opus 5.5)
- 플러그인/스킬: `policy-manager:policy-manager`, `project-docs:ai-usage`

## 요청

- 1Password와의 기능 구조 차이, Secret Key 도입 비용, 서버 호스팅의 의미, 보안 점검 도입 가능성, 로그인 방식의 안전성 비교를 물었고, 잠금 해제 정책 도입과 자동 완성 후속 처리를 지시했다.
- 이어서 추상화·의존성 역전으로 교체 비용이 낮은데 결정마다 신중한 것은 설계가 잘못된 것이 아닌지 물었다.

## AI 산출물

- 1Password 비교: Secret Key(2SKD), SRP 로그인, 항목 단위 암호화와 여러 볼트·공유, 항목 종류, Watchtower, 생체 잠금 해제, 계정 복구, 호스팅 주체 차이를 정리했다. 가장 본질적인 차이로 Secret Key(서버 유출 시 오프라인 대입 차단)와 볼트 전체 단일 암호문 구조(공유·용량 한계)를 들었다.
- 로그인 방식 비교: SRP의 이점은 TLS가 뚫린 상황과 가짜 서버 방어에 집중되고, 서버 DB 유출 시에는 두 방식이 비슷하므로 Secret Key 투자가 더 효과적이라는 판단.
- 설계 질문에 대한 답: 추상화는 코드를 숨기지 데이터를 숨기지 않는다. 입력·출력이 그대로인 교체는 구현체만 바꾸면 되지만, 입력이 늘거나(Secret Key) 주고받는 방식이 바뀌면(SRP) 인터페이스와 사용하는 쪽도 바뀐다. iOS·웹이 코드를 공유하지 않으므로(ADR-0004) 암호 계약 변경은 양쪽 구현과 명세를 함께 바꿔야 한다. 배포 전에는 대부분의 결정이 싸고, 비용이 뛰는 시점은 첫 배포 후다.
- [`docs/policies/SEC/SEC-003-unlock-and-auto-lock.md`](../../policies/SEC/SEC-003-unlock-and-auto-lock.md) 작성, COM-001에 잠금 시 클립보드 즉시 비움 추가, open-questions의 마스터 비밀번호 변경 항목에 Secret Key 검토 추가, 루트 CLAUDE.md 정책 확인 규칙 수정.

## 사람의 판단

- 잠금 해제 정책을 도입하고 자동 완성은 후속으로 미뤘다.
- 결정 확인 절차가 과하다고 판단해, 되돌리기 쉬운 결정은 추천 기본값으로 진행하고 되돌리기 비싼 결정만 확인받도록 규칙을 바꾸는 데 동의했다.
- SEC-003은 제안한 기본값(자동 잠금 5분, 생체 인증 선택, 14일마다 마스터 비밀번호 확인, 잠금 시 클립보드 비움)으로 확정했다.
- Secret Key는 마스터 비밀번호 변경(키 교체) 흐름을 만들 때 함께 정하기로 미뤘다.
